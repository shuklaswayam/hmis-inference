# Architecture

How the HMIS Intelligence Platform is put together, and the contracts between
each layer. Aimed at engineers extending or operating the system; for the
end-user surface see `frontend/FRONTEND.md`.

## Bird's-eye view

```
                    ┌─────────────────────────────────┐
                    │  Gujarat HMIS facility systems  │
                    │   (HMIS portal, e-Hospital, …)  │
                    └──────────────┬──────────────────┘
                                   │ POST metrics + disease reports
                                   ▼
┌─────────────────────┐    ┌─────────────────────┐
│  frontend (SPA)     │◄──►│   FastAPI backend   │
│  React + TS + Vite  │    │   (uvicorn :8000)   │
└─────────┬───────────┘    └─────────┬───────────┘
          │                         │
          │ WS /ws/alerts           │ asyncpg
          │                         ▼
          │                ┌─────────────────────┐
          │                │  Timescale/Postgres │
          │                │  + migration table  │
          │                └─────────┬───────────┘
          │                          │ SQL/CTE
          │                          ▼
          │                ┌─────────────────────┐
          │                │  Rules engine       │
          │                │  + AnomalyDetector  │

          │                │  + DiseaseForecaster│
```

The same FastAPI process is the only public interface; everything else is
internal. Alert creation never depends on the LLM (deterministic rules +
anomaly scoring), so the critical-path service stays up even when Groq is
degraded.

## Layer contracts

### 1. Ingestion (`backend/routers/ingest.py`)

- **Input**: Pydantic-validated payloads (`DistrictCreate`,
  `DiseaseReportCreate`, `FacilityMetricsCreate`).
- **Surface**: `POST /api/v1/ingest/{district,disease_report,facility_metrics}`.
- **Output**: a single row per call, written via asyncpg.
- **Failure mode**: invalid bodies → 422; bad SQL → 400 surfaced from
  `asyncpg.exceptions`. The endpoint does **not** trigger inference — it
  stores the row and lets the rules engine pick it up on the next
  `GET /api/v1/alerts/` call or the nightly Celery task.

### 2. Detection (`backend/rules_engine.py` + `backend/ml/`)

The detection path is shared by the live `GET /api/v1/alerts/` endpoint, the
`GET /api/v1/insights/{facility_id}` endpoint, and the nightly Celery task.

```
facility_metrics  ──► HMISRulesEngine.evaluate()  ──► rule_flags (list)
                              │
                              ▼
                       AnomalyDetector.score()  ──► anomaly_score
                              │
                              ▼
                       AnomalyDetector.z_score_check()  ──► z_scores
                              │
                              ▼
                       RiskScorer.score()  ──► priority_rank ∈ {HIGH, MEDIUM, LOW}
                              │
                              ▼
              HIGH? ──► DiseaseForecaster.forecast_7day()  ──► forecast
                              │
                              ▼
                    LLMSynthesizer.synthesize() (Groq/Ollama) ──► narrative
                              │
                              ▼
                       INSERT INTO inference_results
                              │
                              ▼
                  Redis pub "new_alerts" (HIGH severity only)
```

- **RiskScorer** is pure rule logic — *no model artifact*. The thresholds are
  in `backend/ml/risk_scorer.py` (seasonal weights, anomaly Z-score cuts).
- **AnomalyDetector** uses IsolationForest. The trained classifier is loaded
  from `models/isolation_forest.pkl` (gitignored — generated by
  `scripts/train_anomaly_model.py`).
- **DiseaseForecaster** uses Prophet. Currently trained **per request** on
  the last 90 days of disease_reports, not pickled. If retraining time
  becomes a bottleneck, model caching belongs here.
- **LLMSynthesizer** only runs on HIGH-priority results. It summarises
  `(context, rag_chunks)` into `{what_is_happening, why_it_happening,
  recommended_action}` via Groq (default) or Ollama (offline). The provider
  is selected by `LLM_PROVIDER` and the response is cached in Redis for 5
  minutes on the QA endpoint.

### 3. RAG over policy PDFs

```
backend/data/policy_docs/*.pdf
        │
        ▼  scripts/ingest_policies.py  (manual / CI step)
        ▼
backend/rag/embedder.py  ──► ChromaDB (./chroma_db/, bind-mounted)
        │
        ▼  backend/rag/retriever.py
QA queries  ──► top-5 chunks  ──► LLMSynthesizer  ──► cite-tagged answer
```

- The corpus is seeded with 11 PDFs covering TB, malaria, hypertension,
  Ayushman Bharat, NTEP, immunisation, maternal health, dengue.
- `ingest_policies.py` is idempotent — re-running it does not duplicate
  vectors because chunks are keyed on `[filename]:[hash(slice)]`.

### 4. WebSocket alert stream

```
HIGH-severity alert created in router.alerts → redis.publish("new_alerts", payload)
                                                            │
                                                            ▼
                                                backend/routers/websocket.py
                                                            │
                                                            ▼
                                                  browser receives JSON frame
```

- Single channel: `new_alerts`. The frontend `AlertFeed` reads it via the
  `useWebSocketHook` and falls back to React Query polling when the channel
  is offline.

### 5. Celery task

`backend.tasks.run_nightly_inference` is registered in the beat schedule at
**00:30 IST**. It walks all facilities, runs the same Rule+ML pipeline the
live `GET /api/v1/alerts/` runs, and persists every result in
`inference_results` for backfill / auditability. It binds with `max_retries=3`
and retry-delay `60s`.

### 6. Auth + auth edges

- The whole `/api/v1/*` surface is gated by `APIKeyGate` middleware when the
  `API_KEY` env var is set on the backend. Tests are excluded via
  `PYTEST_CURRENT_TEST`.
- CORS allow-list is controlled by `ALLOWED_ORIGINS` (comma-separated). The
  default is `http://localhost:5173, http://localhost:5174` for local dev.
- WebSocket has no auth — if you expose it, terminate upstream with nginx +
  TLS *and* put the API key check in front of it.

## Data model (Drizzle-ish)

Tables (from `migrations/001_create_tables.sql`):

| Table | Purpose |
|---|---|
| `districts` | Static reference data — name, state, population, zone |
| `health_facilities` | Facility directory including lat/long |
| `facility_metrics` | Daily numeric metrics per facility (Timescale hypertable) |
| `disease_reports` | Disease case counts by date + facility |
| `inference_results` | Append-only log of `alerts` (rules + LLM) —>`expires_at` controls active-window |

Tables (from `migrations/002_add_metrics_severity_columns.sql`):

| Column added | Table |
|---|---|
| `severity` | `inference_results` (high / medium / low) |
| `what_is_happening`, `why_it_happening`, `recommended_action` | `inference_results` |
| `medicine_days_remaining`, `staff_attendance_pct` | `facility_metrics` |

Migration files use `CREATE TABLE IF NOT EXISTS` so replaying on a hot DB
won't fail.

## Operational boundaries

- **Stateless API** — scale by adding uvicorn workers (`--workers N` in
  compose); no sticky session needed.
- **Celery worker** can scale horizontally by adding replicas. The beat
  scheduler must be a singleton.
- **Postgres** — one writer is fine for typical analytics; Timescale chunks
  `facility_metrics` by month. For heavy backfills, prefer `docker compose
  exec backend python scripts/seed_data.py` direct invocation rather than
  running through the API.
- **Redis** — keep it co-located with the API host. Sub-millisecond pub/sub
  is the whole point; a cross-AZ Redis adds 2-10 ms latency you don't want.
- **ChromaDB** — current setup bind-mounts the on-disk vector store. For
  multi-host, switch to S3/MinIO volume drivers.

## Where to start reading

- New backend endpoint? → start at `routers/`, copy the pattern, register in
  `main.py`, ensure it's covered by `tests/test_routers.py`.
- New rule / anomaly logic? → edit `rules_engine.py` or `ml/*.py`. Update or
  add a corresponding test file under `tests/test_<module>.py`.
- Frontend behaviour change? → `frontend/src/pages/` for the page,
  `frontend/src/components/layout/AppShell.tsx` for shell-level concerns,
  `frontend/src/design/tokens.ts` for any styling tokens.
- Adding a model? → training script in `scripts/`, pickle to `models/`,
  wire loader in `ml/<module>.py`.
